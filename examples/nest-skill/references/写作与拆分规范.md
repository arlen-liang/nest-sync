# nest 内容写作与拆分规范

`logs/` 和 `skills/` 两棵内容树的完整规范。`SKILL.md` 里只有速记版，拿不准时读这份。

设计前提（为什么长这样）：

- **recall 和将来的 MCP 只认一种结构**，形态统一换来工具简单
- **上下文是稀缺品**：唤回一个项目默认只该花几十行，细节按需再钻
- **一切元数据从 git 派生**：更新时间 = 提交时间，项目清单 = 目录列表。任何手写的
  "最后更新于"、目录级索引文件都必然过期，禁止引入

---

## 一、日志（logs/）

### 1.1 建项目

```
logs/<项目slug>/INDEX.md
```

- 目录名推荐**英文小写 slug**（`billing-cli`、`docs-site`）：路径稳定、终端友好、
  全局可辨；**中文原名也合法**，胜在与口头称呼一致。两种形态 recall 都能匹配
  （先按目录名，再退回标题/别名）
- 中文名和别名写进 INDEX.md 的标题与"别名"行 —— 别名行给足口头叫法，召回更稳
- **哪怕项目只有一份文件，也建目录 + INDEX.md**。不允许在 `logs/` 下直接放散文件

### 1.2 INDEX.md 模板

```markdown
# <中文名> / <slug>

> 别名：<口头会怎么叫它，逗号分隔>
> 状态：<一句话：进行中到哪一步 / 已上线 / 挂起等>

<一两句话说清这个项目是干嘛的。>

## 当前进度

<三到五个要点。写"现在的状态"，不是流水账 —— 流水账放子文件。>

## 文件索引

| 文件 | 内容 |
|---|---|
| <主题>.md | <一句话说明> |

## 下一步

- [ ] <按重要性排序，最重要的排第一并说明为什么>
```

四个小节一个都不能少 —— recall 默认只回 INDEX，这四节就是别人（包括三个月后的自己）
对项目的全部第一印象。

**不要写的东西**：手写日期（git 有）、与其他项目重复的通用说明（链过去）、真实主体信息
（用 `[项目A]` 代号）。

### 1.3 子项目与深度（递归规则）

**任何项目目录下都可以再建子项目**，规则与顶层完全相同：一个目录 + 一份 INDEX.md。
深度不设上限，recall 对任意深度的节点都能按名字直接唤回。

**但要不要往下拆一层，用这句判断：**

> 「这一层需要**独立的状态和进度叙述**吗？」

- 需要（一件事有自己的进展、下一步、多份文件）→ 建子项目
- 不需要（只是资料归类）→ 用子文件或文件名前缀就够了，别为归类制造目录

父节点的 INDEX 里**不用手工罗列子项目清单** —— recall 展示节点时会自动列出子项目和
更新时间（从目录结构与 git 派生）。文件索引表里只登记值得加一句说明的**直属文件**，
不要把子目录写进去（`nest bind` 生成的模板在该节带提示注释）。
**建/删/大改子项目后，回看一眼父 INDEX 的状态行与进度是否还准** —— 手排清单会烂，
状态行也会烂。

容器节点的 INDEX 往往很短：定位一句话 + 约定，这是正常的。

命名注意：recall 是**全树匹配**，子项目 slug 尽量全局可辨。带时间或编号的实体建议
带上年份或编号片段（`2026-acme-project`），别叫 `demo1`。

### 1.3b 拆分规则

| 对象 | 限高 | 超了怎么办 |
|---|---|---|
| INDEX.md | 约 150 行 | 把细节挪进子文件，索引表加一行 |
| 子文件 | 约 400 行 | 按主题再拆，或按时间断卷（`踩坑记录-2.md`） |

- 限高是**软性**的：超过就该动手，但不必为了凑行数硬拆
- 拆的单位是**主题**，不是章节 —— "决策记录""踩坑记录""某轮测试"各成一件事
- 子文件名用中文没问题，第一行必须是 `# 标题`，recall 靠它显示
- **写进度先更 INDEX，写细节进子文件** —— 顺序反了 INDEX 就会烂掉

### 1.4 日常写作流

```
nest recall <项目>          # 先看现状，别凭记忆写
编辑 INDEX 的进度/下一步     # 状态变化
编辑或新建子文件             # 具体记录
nest sync -m "说明"          # 回传
```

新会话接手一个项目，第一动作永远是 `nest recall <项目>`，不是翻目录。

### 1.5 工作目录与门牌（.nest）

**项目资料**（素材、原始数据、附件）住在各自的工作文件夹里，**不进仓库**；
项目的**日志与备忘**住在仓库的 `logs/<节点>/` 里。门牌把两者对上号：

```
工作文件夹/.nest          一行 node=<节点路径>，纯指针，不是仓库、不含内容
```

- `nest bind [slug]` 立门牌；节点不存在会按 §1.2 模板自动建 INDEX。
  **建节点与立门牌是同一个动作**：别绕过 bind 直接在仓库里裸建节点；确需手工建
  （如批量迁移），必须同时到工作文件夹写门牌，否则云端有节点、本地没指针，唤不回
- 门牌嵌套映射节点嵌套：子文件夹 bind 自动挂在最近祖先门牌的节点之下，
  与 §1.3 的递归规则严丝合缝 —— 要不要给子文件夹立门牌，用同一句判断
- 有门牌的文件夹里 `nest recall` 不带参数直接唤回本项目；`nest recall --all` 看全局
- "更新一下"的含义：把**日志和备忘**写进 `logs/<节点>/`，然后 `nest sync`。
  项目资料本身一个字节都不进仓库 —— 工作文件夹不是 git 仓库，这是物理保证
- 换机器时门牌不同步（它是本地文件），在新机器的工作文件夹里重新 `nest bind`
  一次即可，节点内容云端都有

## 二、技能（skills/）

### 2.1 放哪个大类

技能的**版本演进不需要任何额外机制** —— Git 就是版本史：
`git log --oneline -- skills/<大类>/<技能>/` 看全部演进，需要对比就
`git diff <旧提交> -- <路径>`。SKILL.md frontmatter 里的 `version:` 是给人看的语义标记，
大改时手动升一下即可，不强制。

大类怎么分由使用场景决定，一个常见的三分类：

| 大类 | 放什么 | 判断句 |
|---|---|---|
| `meta` | nest 自身、通用工作方法论 | "任何设备、任何场景都可能用到吗？" |
| `work` | 特定业务领域的方法与流程 | "离开这个业务领域，这个技能还有意义吗？没有 → 放这" |
| `personal` | 个人写作、阅读、个人项目工具 | 其余 |

拿不准就问一句："这个技能会在工作设备上用吗？会在个人设备上用吗？"两个都会 → `meta`。

### 2.2 技能目录结构

```
skills/<大类>/<技能名>/
├── SKILL.md          # 必须。frontmatter 的 description 决定 agent 何时加载它
├── references/       # 可选。详细规范、长篇参考，按需读取
└── scripts/          # 可选。可执行脚本
```

- 技能名用英文小写连字符（`case-review`），软链后就是 harness 里的技能名
- **同一技能绝不在 harness 目录里维护第二份** —— 改真身，`nest link` 后各端生效
- description 要写**触发条件**（用户提到什么词、什么场景时加载），不是功能简介

### 2.3 SKILL.md 自身的拆分

SKILL.md 超过约 300 行，就把"必须当场遵守的"留下，"需要时才查的"挪进 `references/`。
本技能（nest 自己）就是这么拆的：日常用法在 SKILL.md，装机说明与写作规范在 references/。

判断依据是**加载频次**，不是篇幅：每次唤起都要载入的内容留在 SKILL.md，一台机器只做
一次的操作挪进 references/。SKILL.md 的体积是每次唤起都要付的税。

### 2.4 迁入现有技能

1. **有选择地迁**：方法论型（跨设备可复用）进仓库；本机环境型（依赖特定路径、
   特定安装）不进
2. 迁入前过一遍红线：技能文件里不能有 API key、token、本机绝对路径里的敏感信息
3. `git mv` 不适用（源不在仓库里），直接复制进对应大类，然后**删掉原目录**，
   让 `nest link` 建软链回去 —— 否则就违反了"绝不两份"
4. 迁完 `nest sync`，到另一台设备 `nest pull` 验证软链生效

## 三、给未来 MCP 的约定（写作时就要守住）

将来的 MCP 是目录结构上的只读薄层，这些约定破了它就得加补丁：

- `logs/` 一级只有项目目录，没有散文件
- 每个项目目录必有 `INDEX.md`，且首行是 `# 标题`
- `skills/` 一级只有大类目录，二级才是技能
- 不引入任何需要手工维护的索引/清单文件
