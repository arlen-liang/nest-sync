# nest 跨设备技能库与日志库

nest 把技能（skills/）与日志（logs/）放进同一个 Git 仓库，所有设备、所有 harness
共享同一份来源。任一端的更新回传后，其他端拉取即生效；项目日志可以按名字唤回，
不必手动翻找。

**Git 仓库是唯一权威。** 所有命令都只是它的包装。

---

## 第一步：判断当前机器处于什么状态

任何 nest 相关任务，先跑这一句，再决定走哪条路：

```bash
N="$(command -v nest || echo "$HOME/.nest/bin/nest")"; [ -x "$N" ] && "$N" status --no-fetch || echo "NOT_INSTALLED"
```

不要只看 `command -v` —— 新 shell 里 PATH 常常没带上 `~/.nest/bin`，会把装好的机器
误判成没装，然后重复克隆。上面这句会顺带检查默认安装位置。

`--no-fetch` 不能省：判断装没装不需要联网。真正的同步状态由后面的 `pull` / `recall`
各自 fetch 得到，这一步只管"装没装"。

- 输出同步状态 → 已装好，看下面的**日常使用**
- 输出 `NOT_INSTALLED` → 再用 `ls -d ~/.nest*/bin/nest 2>/dev/null` 扫一眼非默认位置的
  副本；确实没有才走装机流程，**读 `references/接入与配置.md`**。仓库位置是死约定
  （`~/.nest/git`），不是每台机器自己挑的
- 命令在但报错找不到仓库 → 看文末**故障排查**

## 内容组织（速记版）

完整规范在 `references/写作与拆分规范.md`，新建项目、迁技能、拿不准怎么拆时**先读它**。

**日志（logs/）**

- 每个项目一个目录 + `INDEX.md`；目录名推荐英文小写 slug，中文原名也合法，
  中文名和别名写进 INDEX 标题与「别名」行，两种写法 recall 都能唤回
- INDEX 四节缺一不可：状态行、当前进度、文件索引、下一步；限高约 150 行
- 细节写子文件（约 400 行再拆）；**先更 INDEX 再写子文件**，顺序反了 INDEX 会烂掉
- **项目可递归**：任何项目下可再建子项目（同样是目录 + INDEX），判断句是
  「这一层需要独立的状态叙述吗？」；只做归类就别建目录。子项目清单不手写，recall 自动列出
- 不手写日期、不建索引文件 —— 时间和清单一律由 git 派生

**技能（skills/）**

- 大类目录自行约定，例如 `meta`（通用）/ `work`（业务）/ `personal`（个人）
- 迁入有选择：方法论型进仓库，本机环境型不进；迁完删原目录让软链接管，绝不两份
- SKILL.md 超约 300 行就把"需要时才查的"挪进 `references/`

**写作流**：`nest recall <项目>` 看现状 → 改 INDEX → 写子文件 → `nest sync -m "说明"`

## 日常使用

### 在项目工作目录里工作（.nest 门牌）

项目资料（素材、图片、附件）住在各自的项目文件夹里，**不进仓库**；对应的
进度与备忘住在仓库的 `logs/<节点>/` 里。`.nest` 门牌把两者对上号：它只是一个指针文件，
记录本目录对应 `logs/` 下哪个节点。

四条铁律：

1. **仓库永远只有一份**（`~/.nest/git`），绝不在工作目录里再 clone 一份 —— 门牌只是指针
2. **"更新一下"= 只写日志和备忘录**进 `logs/<节点>/`。**绝不把项目资料本身（Word/PDF/任何
   二进制）推进仓库** —— 工作目录根本不是 git 仓库，这是物理保证，别绕过它
3. 日志涉及真实主体（合作方、同事）一律用 `[项目A]` 这类代号
4. **建节点与立门牌是同一个动作** —— 用 `nest bind` 一次完成，别在仓库里裸建节点后
   忘了补门牌，否则云端有节点、本地没指针，下次唤回就找不着

第一次在某个工作目录里动手，先立门牌：

```bash
nest bind                      # 直接用文件夹名做节点名（英文 slug、中文原名均可）
nest bind 2026-acme-project    # 想另起名字时显式给
```

- bind 会按模板建好节点的 INDEX.md（云端已有该节点则直接挂上）
- **门牌可以嵌套**：在子文件夹里再 bind，自动挂到上级节点之下 —— 目录嵌套 = 云端项目嵌套
- 已绑定的文件夹里 `nest bind` 不带参数可随时查看绑定与日志目录；解绑就删 `.nest`
  文件，云端内容不受影响

### 开工前

```bash
nest pull
```

拉取云端最新并重建技能软链。有未提交的本地改动时它会停下来提示，此时选：
`nest push` 先回传，或 `nest pull --autostash` 临时收起改动、拉完自动恢复。

### 收工后

```bash
nest push -m "简要说明这次改了什么"
```

会先列出变更文件让人确认。云端若已领先，它自动 rebase 后重试一次，只有**同一文件
两端都改过**时才会停下来要求人工合并。非交互环境（脚本、agent）必须加 `-y`。

**收工自检（push 前必做）** —— 这次会话里：

1. 项目状态变了吗 → 更 INDEX 的进度/下一步
2. 做了值得记住的取舍吗 → 决策记录补一行（含原因）
3. 踩了坑吗 → 踩坑文档补一条
4. 建/删/改了子项目吗 → 回看一眼父节点 INDEX 的状态行与进度是否还准

改了工具/技能却不含 `logs/` 更新时，push 会主动提醒。"代码推了、日志没写"是最常见的
失忆形态 —— 三个月后没人记得为什么这么改。

### 懒人用法

```bash
nest sync -m "简要说明"
```

等于「先 `pull` 再 `push`」。顺序不能反 —— 先把云端的拿下来再送自己的上去，否则本地
提交基于过时历史，push 必然被拒后再绕一圈 rebase。拉取那一半带 `--autostash`，
所以工作区脏也能直接用。

### 唤回项目日志

```bash
nest recall                 # 顶层总览；在有门牌的文件夹里则直接唤回绑定的项目
nest recall --all           # 强制顶层总览（无视门牌）
nest recall <项目>          # 节点统括：INDEX + 子项目列表 + 直属文件
nest recall <项目> <关键词> # 钻取：先匹配子项目，再匹配子树内文件
```

项目可以嵌套，任意深度的节点都能按名字直接唤回。

**这条命令是纯只读的** —— 它只做 `git fetch` 加读取，绝不修改工作区。所以在你正改着
文件、工作区脏的时候照样能用，而那正是最需要它的时候。

输出会说明四种状态之一：

| 状态 | 含义 | 该做什么 |
|---|---|---|
| 同步 | 两端一致 | 直接用 |
| 云端已更新，本地是旧版 | 别的设备推过新内容 | `nest pull` |
| 本地有未推送的改动 | 你改了还没回传 | `nest push` |
| 两端都改过 | 需要合并 | `nest pull` 走 rebase，冲突时人工处理 |

匹配到多个会列出候选；一个都没匹配到会列出最近更新的若干条日志。

### 查看差异

```bash
nest status
```

### 技能改完之后

技能真身在 `~/.nest/git/skills/<大类>/<名字>/`，各 harness 的技能目录是**软链**过去的。
直接改真身，所有 harness 立即生效，然后 `nest push` 回传。

**绝不要在 harness 的技能目录里维护第二份副本。**

## 红线

**以下内容绝不能提交进这个仓库：** API key、token、密码、证书私钥、个人隐私资料。

仓库有两道自动扫描闸门（本地提交时一次，服务端接收时再一次），但闸门只认已知格式，
**不替代判断**。日志涉及真实主体时一律用 `[项目A]` 这类代号。

判断标准：**只放"丢了会心疼但不致命"的东西。**

二进制和图片也不入仓 —— 一旦进了 Git 历史就永久占空间且删不干净。

密钥不做多端同步，这是明确的设计决定：换设备时手动配置各平台凭证。理由见
`docs/security-model.md`。

## 故障排查

| 症状 | 原因与处理 |
|---|---|
| `nest: command not found` | PATH 里没有 `<NEST_HOME>/bin`，见 `references/接入与配置.md` 安装步骤末尾的提示 |
| `找不到仓库 …` | 仓库没克隆或被删，重跑安装步骤；非默认位置需设 `NEST_HOME` |
| `Permission denied (publickey)` | 钥匙没获批，或 `-i` 路径写错 |
| clone 成功但身份不对 | `~/.ssh/config` 有同名 Host 块抢先用了别人的钥匙。用 `core.sshCommand` 固定自己的钥匙 |
| `ssh -T` 报 `Interactive git shell is not enabled` | **这是成功**，不是错误 |
| pull 提示有未提交改动 | `nest push` 先回传，或 `nest pull --autostash` |
| rebase 冲突停住 | 手工改完冲突文件后 `git -C ~/.nest/git rebase --continue`；放弃则 `--abort` |
| 提交时报 `Author identity unknown` | 仓库没配 git 身份。`bash ~/.nest/git/install.sh --name <你的标识>` 补一次（只写本仓库） |
| 提交被拒，提示命中密钥规则 | 真有密钥就删掉改写；确认误报可 `git commit --no-verify`，但服务端还有一道 |
| 技能改了但 harness 没生效 | 跑 `nest link`；确认改的是仓库里的真身而非软链副本 |
| `nest link` 说没找到 harness 目录 | 该 harness 未安装，或目录名不在识别列表内，用 `NEST_LINK_TARGETS` 显式指定 |
| 软链被同名真实目录挡住 | 若那是接入前手动放的临时副本，用 `nest link --force`（会先备份成 `<名字>.bak-时间戳`） |
