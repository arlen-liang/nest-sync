## 核心约定（写任何技能前必读）

### 文件布局

```
skills/<大类>/<kebab-case-英文名>/
├── SKILL.md          # 主文件，日常执行只读这个
└── references/       # 按需加载：注册表、格式规格、措辞语料、类型规则
    ├── xxx-registry.md
    └── xxx-spec.md
（可选）scripts/       # 需要复用的可执行脚本
（可选）templates/     # 需要复用的模板文件
```

- 目录名用英文 kebab-case（`contract-review`、`sanhui-witness`），**不用中文名**
- SKILL.md 保持精简（百来行），厚重内容（清单、语料、格式细节、注册表）一律下沉
  references，SKILL.md 末尾给"按需加载表"

### frontmatter 规范

```yaml
---
name: <与目录同名>
version: 0.1.0
description: >
  <一句话说清做什么、输入什么、产出什么>。
  触发词：<中文触发词 8-15 个，覆盖用户的各种说法>。
  <边界：什么听起来像但不该触发的情形，或"用户说XX时也应触发"。>
---
```

- 触发词宁滥勿缺，包括"帮我做XX""出XX""起草一下"这类口语说法
- 版本号规则：**流程/结构调整 → 大版本；清单/参考文件更新 → 小版本；措辞修正 → 修订号**

### SKILL.md 正文骨架（house style）

按此顺序，各节标题可微调但要素不缺：

1. `# 中文技能名`
2. `## 版本记录` — 表格：版本 | 日期 | 变更内容。**初版注明源自哪次实操**
3. `## 前置条件与红线` — 开工前必须满足的条件 + 不可逾越的线
4. `## 执行流程` — 分 Step，**Step 0 固定为"接单确认"**，最后一个 Step 固定为"验证/交付"
5. `## 重要规则` — 编号列表，全流程中最易犯的错，一句话一条
6. `## 参考文件（按需加载）` — 表格：文件 | 加载时机

### 标志性设计模式（新技能默认都要有）

1. **Step 0 接单确认**：列出开工前必须确认的信息，注明"用户消息中已给的不再追问"；
   信息不全时一次问完，不要挤牙膏式追问
2. **渐进式加载**：SKILL.md 只写流程与规则；类型清单、格式规格、措辞语料放 references，
   注明加载时机
3. **注册表**：凡会"越用越多"的东西（类型、模板、语料）都建 registry，
   每次项目结束后更新
4. **红线**（所有技能必写）：材料本地处理不上传外部服务；原始资料只读；
   临时文件放 `/tmp` 用完即删
5. **复用既有格式**：产出结构化文件时复制既有文件做模板、做最小改动，不从零排版
6. **交付前强制自查**：提取全文核对，写清"通过标准"（零残留、格式正确等），
   **未通过不得交付**
7. **交叉审阅闭环**（最重要的一个模式）：用户微调/复核后，对比差异 → 分析"漏了什么/
   过度标注/措辞改写" → 更新 references 与措辞规则 → 版本记录追加一行。
   技能因此越用越准

## 执行流程

### Step 0：接单确认

1. **技能主题与产出物**（做什么、交付什么文件）
2. **触发词** — 让用户用他自己的话说几遍"以后怎么叫你做这事"，原话就是最好的触发词
3. **从哪次实操沉淀** — 本次会话/项目的操作记录、用户微调反馈就是素材，
   先有实操再有技能，不凭空设计
4. **references 拆分** — 哪些内容会增长（→ registry）、哪些是厚重细节（→ spec）

### Step 1：复盘素材

从实操中提炼，重点挖三类：

- **流程**：实际做了哪几步，顺序是什么，哪步验证过有效
- **坑与解法**：本次踩过的坑写成规则/常见错误
- **用户微调**：用户改了什么 = 用户偏好，写进措辞规则（这是交叉审阅素材的第一手来源）

### Step 2：起草

按骨架填充，参照 `references/skill-template.md`。写完自查：

- 触发词是否覆盖口语说法？边界是否写明？
- Step 0 是否"已给不追问"？红线是否写全？
- 每个 Step 是否可执行（有具体命令、路径、判断标准），没有"认真做好"式废话？

### Step 3：验证

- frontmatter 三要素齐全（name/version/description），name 与目录同名
- 文件树完整：SKILL.md + references/ 中引用的文件都存在
- 模拟触发：用触发词造几个用户句子，确认 description 能匹配
- 通读一遍：去掉只有本次项目才懂、但不影响通用执行的项目专名
  （保留作"源自"记录即可）

### Step 4：汇报与维护

- 向用户说明：技能位置、触发方式、references 结构、以后如何积累
- 技能投入使用后，每次交叉审阅按"标志性设计模式 7"更新，版本号按规则递增

---

## 重要规则

1. **先实操后技能**：从真实项目沉淀，不凭空设计流程；初版版本记录必须注明来源
2. **SKILL.md 精简、references 厚重**；会增长的内容一律 registry 化
3. **触发词宁滥勿缺**，用用户的原话；有歧义时写负向边界
4. **红线写进每个技能**：不外传、原件只读、临时文件清理、交付前自查
5. **交叉审阅闭环是标配**：没有"用户微调后学什么"的机制，就不是完整的技能
6. **版本记录同步更新**：每次改技能（含 references 实质更新）都追加一行，注明来源
