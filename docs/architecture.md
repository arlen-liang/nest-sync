# 系统架构

nest-sync 的全部状态放在一个 Git 仓库里。没有数据库、没有常驻同步进程、没有服务端
应用状态 —— 服务端只有一个裸仓库和三个部署件。所有命令都只是 git 的包装。

## 全景

```
设备（同一台机器上可以住多个 agent，各自独立身份）
  ~/.nest/git/               Git 工作副本；连接用的钥匙由仓库级 core.sshCommand 固定
  ~/.nest/bin/nest           单一脚本，七个子命令；从自身位置反推所属仓库
  ~/.nest/config             可选的本地配置（软链目标、要拉取的大类等）
  <harness>/skills/<name>    单层软链 → 仓库 skills/<大类>/<name>
        │
        │  ssh git@<服务器>（git 用户只能收发仓库，拿不到 shell）
        ▼
服务器
  /srv/git/nest-sync.git     裸仓库；hooks/pre-receive 是绕不过的服务端密钥闸门
  /opt/nest-enroll/          注册受理服务（无权限用户，仅监听回环地址）
  /usr/local/sbin/nest-keys  钥匙名单管理，需要 root 且只能在服务器本地执行
  /var/www/nest/             说明页 + 申请页，整站 HTTP 基础认证
  /var/lib/nest-enroll/      待批队列、已决记录、审计日志
```

三层各自只做一件事：

- **Git** 是唯一事实来源，也是唯一的历史与版本机制
- **bin/nest** 是本地包装层，负责同步、唤回、绑定与软链
- **deploy/** 是准入层，负责"谁能连上这个仓库"

## bin/nest 的子命令

| 命令 | 用途 |
|---|---|
| `nest sync [-m 说明] [-y]` | 一次搞定：先拉后推。顺序不能反，否则本地提交基于过时历史 |
| `nest pull [--autostash]` | 开工前拉云端最新（rebase），并重建软链 |
| `nest push [-m 说明] [-y]` | 收工后回传；被拒时自动 rebase 重试一次。非交互环境必须 `-y` |
| `nest recall [项目] [关键词]` | 唤回项目。**纯只读**，默认只回 INDEX，带关键词才钻子文件 |
| `nest status` | 本地与云端差异 |
| `nest bind [slug\|路径]` | 给工作文件夹立 `.nest` 门牌，绑定到 `logs/` 节点 |
| `nest link [--force]` | 重建 skills 软链；自动识别 harness，按大类过滤 |

### 仓库定位：从脚本自身位置反推

`nest` 支持多份副本共存（例如同一台机器上不同 agent 各装一份）。定位顺序是：

```
NEST_BRAIN > NEST_HOME > 脚本自身位置 > 默认 ~/.nest/git
```

**"脚本自身位置"这一条是关键。** `install.sh` 把 `<仓库>/bin/nest` 单层软链到
`<NEST_HOME>/bin/nest`，解析一层软链后向上两级就是仓库根。没有这一步的话，同一台机器
装了多份 nest 时，在没设环境变量的新 shell 里调用任何一份，都会退回到默认路径 ——
操作到别人的仓库上去。这也是为什么 `NEST_HOME` 不需要持久化到 shell 配置里。

### 软链分发技能

技能真身在仓库的 `skills/<大类>/<技能>/` 下，各 harness 的技能目录里放的是**单层软链**。
改真身，所有 harness 立即生效；不存在"第二份副本"漂移的可能。

两条实现细节：

- 一律用 `ln -sfn`。不带 `-n` 时第二次重建会把链接建到目录内部（`skills/x/x`）
- `nest link` 是幂等的：清理失效软链、移除未选大类的软链、**跳过同名真实目录**
  （那是本地自有技能，不覆盖）与指向其他副本的软链

仓库全量同步，但每台设备可以只挂载需要的大类（`NEST_LINK_CATEGORIES`）。
选择发生在软链层，不在同步层 —— 副本永远是完整的，MCP 之类的只读接口不需要理解
"这台机器上有什么"。

### bind 门牌机制

工作底稿（合同、素材、原始数据）住在各自的项目文件夹里，**不进仓库**；对应的进度与
备忘住在仓库的 `logs/<节点>/` 里。门牌把两者对上号：

```
<工作文件夹>/.nest        一行 node=<节点路径>，纯指针
```

- 门牌**不是仓库副本**，内容永远只有一份。它的作用是指出"本目录对应云端哪个节点"
- 门牌**可以嵌套**：子文件夹里的门牌默认挂在最近祖先门牌的节点之下，目录嵌套映射
  为云端节点嵌套
- 因为工作文件夹根本不是 git 仓库，底稿**物理上**推不进云端 —— 这是结构性保证，
  不是纪律要求
- 有门牌的目录里，裸 `nest recall` 直接唤回绑定的项目；`--all` 才看全局

节点名规则是**结构黑名单**而非白名单：不能为空或全空白、不能含 `/` 或 `\`、不能以
`.` 或 `-` 开头、不能含控制字符。中文名合法 —— 让工具去适配现实中的命名方式，
而不是反过来。

## recall：只读、三方比对、按需下钻

`recall` 是整套系统里最有价值的一条命令，它的设计约束是"任何时候都能用"：

- **只做 `git fetch` 加读取，绝不修改工作区。** 所以工作区脏的时候照样能用 ——
  而那正是最需要它的时候（如果 recall 依赖 pull，而 pull 在脏工作区会停下，
  就会出现"越需要越用不了"）
- **三方比对**（工作区 / HEAD / 远端）而不是两端比对。只比两端只能得出"不一致"，
  三方才能区分"云端更新了"和"你本地没推"
- **默认只回 INDEX + 文件列表**，带上关键词才钻子文件。上下文占用由查询深度决定

离线时 `fetch` 只警告不中断，recall 退回到上次同步的版本继续工作。

## 内容结构即接口

```
logs/<项目>/INDEX.md        统括：状态、进度、文件索引、下一步。上限约 150 行
logs/<项目>/<主题>.md       具体记录。超约 400 行再拆
logs/<项目>/<子项目>/       递归：含 INDEX.md 的目录即节点，深度不设上限
skills/<大类>/<技能>/       SKILL.md + references/ + scripts/
```

三条规则：

1. **节点 = 含 `INDEX.md` 的目录**，这是唯一定义，recall 与将来的只读接口只认这一种
   结构；子项目清单与深度由目录结构派生，不手写
2. **拆分靠 INDEX 限高**，细节按需下钻
3. **元数据全部从 git 派生，不手写**：更新时间 = 最后一次提交时间，项目清单 = 目录列表。
   手写索引必然过期，而过期的索引比没有更糟

结构统一换来的是接口简单。将来若加 MCP，它只是目录结构上的只读薄层，零额外状态：
`list_projects` = 顶层节点 + 最后提交时间；`get_project` = INDEX + 子项目 + 直属文件；
`get_skill` = 读技能文件。

**不做写操作。** 让接口直接写云端会让本地工作副本永久落后，双写路径把状态劈成两半。
既然"Git 为真身"，就贯彻到底。

## 服务端：注册受理流程

新设备接入不是自助的，需要一次人工核对：

```
1. 申请方在自己机器上生成 ed25519 密钥对
2. 用站点提供的用户名密码，向受理接口提交「标识 + 公钥」
3. 受理服务校验格式（严格只收 ed25519、单行、长度受控），算指纹，落进待批队列
   返回申请 id 与指纹
4. 申请方通过另一个渠道（对话/当面）把指纹报给管理员
5. 管理员在服务器本地执行 nest-keys approve <id> --fingerprint SHA256:xxx
   脚本做三重校验：申请里的指纹、管理员抄的指纹、公钥现算的指纹，三者必须一致
6. 通过后写入 git 用户的 authorized_keys，每行带
   no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty
7. 申请方 clone 并跑 install.sh 完成初始化
```

第 4 步是整个流程的安全根基：站点密码是共享的，只能挡住扫描器；真正拦住冒名提交的
是这次跨渠道的指纹核对。详见 [security-model.md](security-model.md)。

## 设计边界

- **单点。** 服务器上的裸仓库是唯一权威副本。各设备的工作副本不构成独立备份 ——
  它们最终都回到同一台服务器。需要第三个物理位置才算真有备份
- **不适合大文件。** 仓库是纯文本导向的，二进制与图片不入仓；仓库大了之后
  clone 与 fetch 的时间都会线性增长
- **手动触发。** 第一阶段不挂自动 hook，靠"开工前 pull、收工后 push"的约定。
  自动化留给后面按真实痛点决定
