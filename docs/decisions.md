# 设计决策记录

按主题记录关键取舍与原因。格式是"决定 / 为什么 / 代价"—— 只写结论不写原因的记录，
三个月后没人看得懂。

## 基础设施

### 用 Git 而不是实时同步服务

**决定**：以 Git 仓库为唯一事实来源，所有操作是 git 的包装，同步由人手动触发。

**为什么**：

- 版本历史、冲突检测、差异比较、离线可用，这四件事 Git 全都现成，自建同步服务要
  各写一遍
- 内容本身就是文本（Markdown + 脚本），Git 的强项
- 冲突处理有明确的、人已经熟悉的语义。实时同步服务面对"两端同时改"时通常只能选
  一边赢，而日志恰恰是两端都可能改的内容
- 不引入常驻进程，没有"服务挂了我不知道"的状态

**代价**：没有实时性，靠约定（开工前 pull、收工后 push）。多设备同时改同一文件时
需要人工合并。

### 手动触发，不挂自动 hook

**决定**：第一阶段全部手动触发；只在 push 时对"改了工具却没更新日志"做提醒，不拦截。

**为什么**：先跑一段时间手动流程，确认真实痛点再决定自动化什么。过早自动化会把
猜错的工作流固化下来。

**代价**：依赖使用者的自觉。留痕提醒只提醒不拦截 —— 拦截会把误报变成障碍，
而"忘了写日志"的代价只是后来的人要多翻一次提交历史。

## 同步语义

### pull / push 一律走 rebase

**决定**：拉取用 rebase；push 被拒绝时自动 rebase 重试一次，只有真冲突才停下来。

**为什么**：内容仓库里不同文件的并发改动本就能自动合并，只有同一文件被两端都改过
才值得打扰人。merge commit 在这个场景里只增加噪音，不带来信息。

**代价**：rebase 会改写本地提交的哈希。因为只有一个人在同一台机器上操作，
不存在"别人基于我改过的提交继续工作"的情况，代价可以接受。

### recall 是纯只读的

**决定**：`nest recall` 只做 `git fetch` 加读取，绝不触碰工作区。

**为什么**：如果 recall 依赖 pull，而 pull 在工作区脏的时候必须停下来，就会出现
"最需要唤回项目的时候恰好用不了"。只读还带来两个附带好处：可以离线（fetch 失败只
警告不中断，退回上次同步的版本），以及任何时刻都能安全地跑。

**代价**：看到的内容可能不是最新的，所以输出里必须明确标注状态。

### 状态判定用三方比对，不用两端比对

**决定**：比对工作区、HEAD、远端三处的 blob 哈希，而不是只比本地和云端。

**为什么**：只比两端只能得出"不一致"，三方才能区分"云端更新了"（该 pull）和
"你本地改了没推"（该 push）。用户需要的正是这个区分。

**代价**：多一点读取开销，与判断准确度相比可以忽略。

## 内容结构

### 节点 = 含 INDEX.md 的目录

**决定**：项目与子项目的唯一定义是"含有 `INDEX.md` 的目录"，规则递归适用，
深度不设上限。

**为什么**：定义简单到不需要解释，工具的实现也跟着简单（一个递归匹配）。
子项目清单和嵌套深度全部由目录结构派生，不手写。

**代价**：容器层也需要一份 INDEX，哪怕内容很少。这不被认为是成本 —— 它恰好是
"这一层要独立叙述吗"这个判断的落点。

### 砍掉手写的项目索引文件

**决定**：不引入 `project-index.json` 之类的清单文件，项目列表从目录结构派生，
更新时间从 git 提交时间派生。

**为什么**：手写索引必然过期，而过期的索引比没有更糟 —— 它会让人按错误的信息行动。
几十个文件按目录名加首行标题做模糊匹配是毫秒级的，不值得为这点性能引入一份会腐烂的
状态。

**代价**：无法在索引里预置"人写的排序"。这个问题用别名行和命名规范解决。

### 门牌指针，而不是每个项目一份仓库副本

**决定**：工作文件夹里放一个 `.nest` 指针文件指向云端节点，而不是在该目录下 clone
一份仓库。

**为什么**：

- 每个项目一份副本会重复下载、多处漂移，最终没人知道哪份是真的
- 工作文件夹里放着合同、素材、原始数据，一旦它是 git 仓库，就时刻存在"误把底稿
  提交上去"的风险。让工作文件夹**根本不是** git 仓库，底稿就物理上进不了云端 ——
  结构性保证比纪律要求可靠
- 指针只有一行，不存在版本冲突

**代价**：指针是本地文件，不同步；换机器要在新的工作文件夹里重新 bind 一次
（节点内容云端都有，不丢东西）。

### 门牌存完整节点路径，不存相对片段

**决定**：`.nest` 里存的是完整节点路径，而不是相对于父节点的片段。

**为什么**：recall 时向上找到最近一块门牌就可以停下，不必爬到顶层再逐级拼接。
父子关系只在 bind 那一刻参考一次。

**代价**：父节点改名时子门牌不会自动跟着改。改名在实践里极少发生，可以接受。

### 节点名用结构黑名单而不是白名单

**决定**：节点名不限制字符集，只排除结构上会出事的形式：空或全空白、含路径分隔符、
前导 `.` 或 `-`、含控制字符。中文名合法。

**为什么**：现实中项目文件夹就是中文的，工具应当适配现实的命名方式，而不是要求人
为了工具改名。"与工作文件夹一一对应"带来的口播一致性收益，大于字符集收窄带来的
那点可控性。英文小写 slug 仍然是顶层项目的**推荐**形态（终端友好、全局可辨），
但只是推荐。

**代价**：终端里处理中文路径需要确保工具链的编码配置正确（例如 git 的
`core.quotepath`）。

## 技能分发

### 软链分发，仓库全量同步

**决定**：技能真身只有一份在仓库里，各 harness 目录放单层软链；仓库全量同步，
"这台设备要哪些大类"的选择发生在软链层。

**为什么**：多份副本必然漂移，"改了一端另一端还是旧的"正是要解决的问题。
选择放在软链层的好处是同步逻辑不需要知道设备差异，只读接口也不需要理解"这台机器上
有什么"。

**代价**：每台设备仍然下载完整仓库，包括用不到的大类。纯文本仓库的体积增长在相当
长时间内不构成问题。

### SKILL.md 精简、细节下沉 references

**决定**：技能主文件控制在百来行，装机说明、格式规格、语料、清单等挪进
`references/`，按需加载。

**为什么**：**技能文件的体积是每次唤起都要付的税**，而装机说明是只交一次的费用。
两者放在同一个文件里，等于把一次性成本摊成了经常性成本。

**代价**：拆分后必须有导航（一张"什么时候读哪个文件"的表），否则调用方不知道
细节去哪了。这是个真实的成本，但不难付。

### SKILL.md 超过约 300 行就拆

**决定**：以 300 行左右为软性阈值，把"需要时才查的"挪进 references。

**为什么**：阈值是软的 —— 超过就该动手，但不必为了凑行数硬拆。判断依据是加载频次，
不是篇幅。

## 准入与身份

### 密钥不做多端同步

**决定**：仓库只存"凭证放在哪、怎么申请、怎么轮换"这类说明，不存凭证本身。

**为什么**：把凭证放进内容仓库等于把它们复制到每一台设备、每一个 agent 上，
审计时无法回答"这把钥匙现在存在于哪些地方"，怀疑泄露时也无法收敛影响面。
换设备本来就要重新登录各平台，多配一次 key 是几分钟的事，便利度收益有限。

更根本的原因：一旦内容同步工具开始存密钥，它同时就成了凭证分发系统，而后者需要的
权限模型、轮换机制、吊销流程，这个工具一个都没有。详细论证见
[security-model.md](security-model.md)。

### 弃用 SSH 主机别名

**决定**：远程地址直接写完整主机名，钥匙由仓库级 `core.sshCommand` 固定，
不使用 `~/.ssh/config` 里的别名。

**为什么**：SSH 对 `IdentityFile` 是累积并按顺序尝试的。同机器上多个 agent 各写一个
同名 `Host` 块时，排在前面的**别人的钥匙**一旦有效就会被采用 —— clone 会成功，
但用的是别人的身份，而且全程零报错。这个坑只有在查服务端日志时才会发现。

一般化的教训：**在共用账号的环境里，任何"隐式解析"的配置都是身份串用的入口。**

**代价**：命令变长，每个仓库要单独配一次钥匙。用 `install.sh --key` 把这一步自动化了。

### 身份只写仓库级，不写全局

**决定**：`user.name/email` 与 `core.sshCommand` 都写在仓库级配置里（`--local`），
不污染这台机器的其他仓库。

**为什么**：同一台机器上可能有多个副本、多个身份。全局配置既影响无关仓库，也会被
后来的安装悄悄覆盖。仓库级的作用域恰好是"这个副本代表谁"。

**代价**：每个新副本都要配一次（`install.sh --name` 会做）。

### 名字不允许重名

**决定**：批准时拒绝与名单中已有条目同名的申请。

**为什么**：名字是吊销时的唯一凭据（`revoke <name>` 按名字匹配）。允许重名会让一次
吊销砍掉多把钥匙 —— 本该吊销一把，结果把一台正常设备的访问也断了。重名在批准环节
挡住，比在吊销时才发现代价小得多。

### 受理服务与钥匙管理分离

**决定**：收申请的程序没有权限写 `authorized_keys`；写名单的程序需要 root 且只能在
服务器本地执行。

**为什么**：受理服务的输入来自公网，是被攻击面最大的组件。让它即使被完全攻破也只能
往待批队列里塞垃圾，整个系统的安全性就不再依赖那个服务的健壮性。

**代价**：批准是一次人工操作，无法全自助。这是刻意的 —— 跨渠道核对指纹本来就是
这条链路上唯一真正拦住冒名提交的环节。

## 明确不做的事

| 不做 | 原因 |
|---|---|
| 让只读接口直接写云端 | 会让本地工作副本永久落后，双写路径把状态劈成两半。既然"Git 为真身"就贯彻到底 |
| 引入需要手工维护的索引/清单文件 | 必然过期，而过期的索引比没有更糟 |
| 二进制与 Office 文档入仓 | 进了 Git 历史就永久占空间且删不干净，改写历史的代价远高于收益 |
| 依赖第三方服务 | 服务端只有裸仓库加三个部署件，全部可自托管，无外部运行时依赖 |
