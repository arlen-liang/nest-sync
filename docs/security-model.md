# 安全模型

这套系统的安全目标很朴素：**让仓库里永远不出现不该出现的东西，让每一次改动都能追溯到
是谁做的，让丢失一台设备不至于全盘失守。**

边界不追求"防住有决心的攻击者"，而是让常见的失手没有后果。

## 信任边界

```
┌─ 申请方（人 / agent，不信任）────────────────────────────┐
│  公钥、标识、备注      全部按敌意输入处理                 │
└──────────────────────┬─────────────────────────────────┘
                       │  HTTPS + 基础认证（共享密码，只挡扫描器）
┌──────────────────────▼─────────────────────────────────┐
│  受理服务（半信任：只收不批）                             │
│  唯一写权限 = 待批队列目录。被完全攻破也只能塞垃圾          │
└──────────────────────┬─────────────────────────────────┘
                       │  人工跨渠道核对指纹（不可自动化）
┌──────────────────────▼─────────────────────────────────┐
│  钥匙名单管理（信任：root + 仅服务器本地）                 │
│  唯一有权写 authorized_keys 的程序                        │
└──────────────────────┬─────────────────────────────────┘
                       │  SSH：git 用户，无 shell、无转发、无 TTY
┌──────────────────────▼─────────────────────────────────┐
│  裸仓库（信任）                                           │
│  pre-receive 闸门：本地 hook 可绕过，这一道不能            │
└────────────────────────────────────────────────────────┘
```

**一、密钥进不了仓库。** 两道独立闸门：本地 `pre-commit` 与服务端 `pre-receive`。
本地那道可以用 `--no-verify` 绕过（设计如此，误报时得给条出路），服务端那道不能。
两处都先查文件名黑名单（`.env`、`id_rsa`、`*.key`、`*.pem` 等），再做内容正则扫描；
装了 gitleaks 就自动切换到 gitleaks，没装则退回内置规则（AWS / GitHub / OpenAI /
Slack / 私钥块 / 通用 api_key= 模式）。

**二、钥匙只能碰仓库。** 专用 `git` 用户配 `git-shell`，`authorized_keys` 的每一行都带
`no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-pty`，`sshd` 另有
`Match User git` 块兜底。登录不打印任何系统信息（`.hushlogin`）—— 系统信息本身也是
泄露：内网地址、负载、磁盘、待更新数量、OS 版本，对已经拿到钥匙的人正好够用。

**三、受理服务写不了钥匙名单。** 网页服务以无权限用户运行，唯一写权限是待批队列。
真正写 `authorized_keys` 的是另一支需要 root、且只能在服务器本地执行的工具。即使受理
服务被完全攻破，攻击者也只能往队列里塞垃圾。

**四、人工闸门是根基。** 批准时必须显式抄一遍指纹，而指纹应由申请方通过**另一个渠道**
告知。批准工具做三重校验：申请记录里的指纹、管理员输入的指纹、从公钥现算的指纹，
三者一致才写入。这条防的是"看都不看就批"—— 页面密码是共享的，指纹核对才是真正
拦住冒名提交的那一步。

### 被明确拦下的几类输入

受理服务把每个字段都当敌意输入处理，实测拦下的手法包括：

- 公钥里夹换行，试图向 `authorized_keys` 注入额外的钥匙行
- 标识里塞路径穿越字符
- 伪造 `command=` 前缀，想给钥匙挂上额外权限
- 弱密钥（只收 ed25519）与垃圾数据冒充公钥
- 超长请求体、查询接口的路径穿越
- 单 IP 高频提交（限流）、待批队列刷爆（队列上限）

## 数据分级

入仓判断不看"重不重要"，看"泄露了会怎样"。

| 级别 | 内容 | 处理 |
|---|---|---|
| 绿 | 方法论、公开工具用法、个人偏好、流程规范 | 直接入仓 |
| 黄 | 项目进度、复盘、配置备忘录、决策记录 | 去敏后入仓，涉及真实主体用 `[客户A]` 这类代号 |
| 红 | API key、token、密码、私钥、证件与个人隐私资料 | 绝不入仓 |

判断句：**只放"丢了会心疼但不致命"的东西。**

闸门只认已知格式，不替代判断 —— 一个没有特征的项目代号、一句能定位到具体人的描述，
正则永远扫不出来。

## 为什么密钥不做多端同步

这是本项目最早也最明确的一条设计决定。

把 API key、token、平台凭证放进这个仓库，等于把它们复制到每一台接入的设备、
每一个接入的 agent 上。审计时无法回答"这把钥匙现在存在于哪些地方"，也无法在怀疑
泄露时收敛影响面 —— 只能挨个设备去翻。而同步带来的便利度提升有限：换设备本来就要
重新登录各个平台，多配一次 key 是几分钟的事。

**折中方案**：仓库里存"凭证放在哪个平台的哪个位置、怎么申请、轮换周期"这类**说明**，
不存凭证本身。换设备时按说明手动配置。写入 `~/.nest/config` 的本地配置同理不入仓。

更一般的原则：**密钥的生命周期管理属于专门的密钥管理工具，不该由内容同步工具兼任。**
一旦内容同步工具开始存密钥，它就同时成了凭证分发系统，而后者需要的权限模型、轮换机制、
吊销流程，这个工具一个都没有。

## 为什么二进制不入仓

图片、截图、Office 文档一旦进入 Git 历史就永久占空间，而且删不干净 —— 改写历史会
破坏所有副本的提交哈希，代价远高于收益。仓库的定位是纯文本内容库，二进制是外来的
负担。

实际影响：

- 工作底稿（Word/PDF/证据/素材）住在各自的项目文件夹里，一个字节都不进仓库。
  因为那些文件夹根本不是 git 仓库，这是结构性保证而非纪律要求
- 需要在文档之间共享的图片走外部链接或另择存储
- `.gitignore` 默认排除常见二进制与 Office 扩展名

## 身份与追溯

每个访问者 —— 人也好、agent 也好 —— 用**独立的 git 身份 + 独立钥匙**，不混用。
`git log` 的提交署名给出"谁改的"，服务端的 SSH 日志给出"从哪把钥匙进来的"，两者
合起来能回答"这次改动是谁做的"。

- 一把钥匙只属于一个身份：agent 的钥匙不给人用，人的钥匙也不给 agent 用
- 切换身份 = 改仓库的 `user.name/email` + `core.sshCommand`，而不是共用一把钥匙
  只改署名
- 名字是吊销时的唯一凭据，因此**不允许重名** —— 重名会让吊销时无法区分，
  批准环节直接拒绝。吊销时逐条打印被移除钥匙的指纹，避免"以为只吊销了一把"
- 每次批准/驳回/吊销都写审计日志

### 一个真实踩过的坑：SSH 别名会悄悄抢走身份

同一台机器上多个 agent 各在 `~/.ssh/config` 里加一个同名 `Host` 块时，SSH 会把所有
`IdentityFile` **累积起来按顺序尝试**。排在前面的别人的钥匙一旦有效就会被采用 ——
clone 会"成功"，但用的是别人的身份，**全程零报错**。

结论是**弃用 SSH 别名**：远程地址直接写完整主机名，钥匙由仓库级 `core.sshCommand`
固定，`install.sh` 结尾打印本仓库实际使用的钥匙指纹供核对。

一般化的教训：**在共用账号的环境里，任何"隐式解析"的配置都是身份串用的入口。**
显式指定，并且把最终生效的值打印出来给人核对。

## 已知的局限

- **站点密码是共享的**，只能挡住扫描器。它的作用是把公网上的无差别探测挡在门外，
  不是身份认证
- **指纹核对依赖人。** 如果管理员跳过核对直接批准，整套准入链条就断了
- **Git 历史不可改写。** 密钥一旦推进去，即使后续提交删掉，历史里仍然在。所以闸门
  必须在第一次提交时就拦住，而不是事后清理
- **单点。** 服务器上的裸仓库是唯一权威副本，它同时也是备份的单点。设备侧的副本不算
  独立备份，因为它们都回落到同一台服务器
